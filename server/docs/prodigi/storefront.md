# Prodigi storefront launch: Phyllotaxis I

The single reviewed product `moonlit-botanicals-phyllotaxis-art-print` maps to
GLOBAL-FAP-12X16, EMA 200gsm, default print area, 3600×4800 RGB sRGB artwork.
The original design is generated by mathematical code (golden-angle phyllotaxis,
Fibonacci counts and Bezier leaves), with no image generation model. Its source
and editable SVG are in `server/artwork/prodigi`. The code was written with AI
assistance. Public flat-art and detail previews are in `assets/products`.

Retail: USD 44.95 with Standard US shipping included. Initial destination: US.
A fresh country-level Standard quote is required for every checkout. The shop
absorbs supplier US sales tax, which the quote may exclude. A supplier total
above 75% of basket retail blocks checkout pending a price review. Other
suppliers retain their existing delivery and checkout paths.

## Credentials and artwork

The existing root-only key stays at `/etc/tbw-prodigi/api_key`. systemd
`LoadCredential` presents a private copy to the www-data service; its path comes
from `%d`. `PRODIGI_ORDERS_ENABLED=1` enables the store transport's order operation.
This is separate from PR95's quotes-only evaluation client, which is unchanged.
There are no new administrator/MCP order-creation tools.

The print JPEG is deployed outside the web root to
`/var/lib/tbw-prodigi/artwork`. SHA-256, RGB dimensions and ICC are checked.
Only a signed GET/HEAD URL can return the reviewed master to Prodigi. Its
path is an extensionless SHA-256 identifier so nginx static-image regex rules
cannot intercept it; the response declares image/jpeg. No
credentials, signing tokens or buyer addresses belong in application logs.

## Payment and duplicate protection

Checkout first confirms credentials, file and live quote. It freezes the exact
recipient, quantities, SKU, attributes and signed artwork URL in a
`prodigi_submissions` row with a persistent UUID idempotency key before PayPal
checkout. After canonical PayPal capture verification, the existing atomic paid
claim routes Prodigi lines separately from CJ, Printify, Lulu and downloads.
A second atomic claim is committed before the single supplier POST. A timeout,
crash or ambiguous response is held as uncertain and is not automatically resent.
The supplier's returned key/reference/lines are verified where present; minimal
Created/OnHold responses can return an ID only, as documented. Supplier
AlreadyExists is accepted only after identity and line checks.

A reconciliation command makes GET requests only and verifies the frozen key
and exact line mapping before restoring the local supplier reference:

```sh
python scripts/reconcile_prodigi_submission.py --order-id LOCAL_ID --supplier-order-id ord_SUPPLIER_ID
```

Run with the protected runtime credential available. Do not create another
supplier order to recover a timeout. The existing two-hour tracking cron starts a www-data oneshot systemd unit
with the same private credential mechanism. The tracking worker polls accepted
Prodigi orders, requires every shipment to be shipped before marking the leg
complete, and alerts the shop about unsubmitted or problematic legs.

## Deployment

Deploy copies the private print asset, checks the credential, verifies Product
Details and obtains a quote without creating an order. After service restart,
`publish_prodigi_phyllotaxis.py --publish` also fetches and hashes the signed
asset from the running app before idempotently activating exactly this product.
The publisher does not make payments, create supplier orders or post launch pins.
Existing variants retain their IDs. No unrelated product rows are changed.

The order column migration and submission table are additive. To stop new sales,
deactivate this product; disabling PRODIGI_ORDERS_ENABLED additionally makes the
checkout readiness guard fail closed. Preserve submission rows for reconciliation.

## Verification

Offline tests cover transport guards, protected artwork, exact quote payload,
US restriction, pre-payment snapshot, concurrency, uncertain submissions,
read-only reconciliation, importer idempotence, routing, checkout and tracking.
The existing PayPal, worldwide shipping, Lulu and product schema suites also run.
No real payment or supplier order is needed for deployment verification.
